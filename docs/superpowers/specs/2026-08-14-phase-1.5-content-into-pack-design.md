## Scope

`src/data/content.js` moves into `src/packs/de/`, split by concern. Two
categories of German that the move alone would leave behind come with it: the
chat greetings stranded in `ChatTab`, and the last two pieces of German
language knowledge in engine code.

Out of scope: the German-flavoured UI chrome and gamification naming
(~25 strings) — see §6, that gets its own spec. Also `stats.js`'s `LEVELS`.

---

## Why

### The queued description covers about a fifth of what is left

The Tier B queue reads "`src/data/content.js` physically moves into
`src/packs/de/`". That part is genuinely small: 388 lines, seven exports, and
only two importers (`de/index.js` and `packs.test.js:11`).

But German outside the pack falls into three categories, and the move only
addresses one:

**A · Pack content sitting in a component.** `ChatTab.jsx:60-80` holds an
`intros` object with **four** per-scenario opening messages — `free`,
`coffee`, `meet`, `airport` — each shaped `{ de, ipa, en }`, identical to chat
data. Phase 1.3 deferred one of these ("`Hallo! Ich bin Anna…`") to this
phase; there are four.

**B · German language knowledge in engine code.**
`AlphabetTab.jsx:325` hardcodes `['Ä','Ö','Ü','ß']` to tint "special" letters,
and `resolve.js:8` composes `` `${entry.article} ${entry.de}` `` — assuming
the article precedes the noun. The latter is the last item deferred from
Phase 1.4.

**C · German-flavoured chrome and gamification naming.** Rank names
(`Anfänger` → `Muttersprachler`), achievement names (`Drei am Stück`,
`Wochenheld`, `Monatsmeister`), toast copy (`Tagesziel erreicht!`,
`Freeze genutzt`, `Neuer Rekord!`), and UI chrome (`WILLKOMMEN`, `DU`,
`tippt`, `Alles gut!`, `Übersetzen`).

**A and B are in this phase. C is not** — see §6.

### Why C is a different problem

A and B are language *content* and *knowledge* in the wrong place: mechanical
to move, obviously wrong where they are. C is the app's German personality.
Whether a Spanish pack says `¡Objetivo diario!` or keeps `Tagesziel erreicht!`
is a product decision about brand, not a refactor. Deciding it inside a phase
filed as a file move would be the wrong place to decide it.

---

## Decisions

| # | Decision | Choice |
|---|---|---|
| 1 | Scope | **Move + A + B.** C gets its own spec |
| 2 | File layout | **Split by concern** — four modules, matching how `de/` already separates `theme.js`, `decks.js`, `lexicon.js`, `grammar.js` |
| 3 | Greeting shape | **Nested inside each scenario**, not a parallel map |
| 4 | Special letters | **A flag on the alphabet entry**, not a separate list |
| 5 | Article position | **`grammar.articlePosition`**, threaded explicitly like Phase 1.4's `grammar` argument |

Decisions 3 and 4 share a rationale, and it is the one this project keeps
relying on: a value that must agree with another value should live *inside*
it, so disagreement becomes structurally impossible rather than merely
unlikely. Same argument as `displayPerson ∈ personKeys` in Phase 1.4.

## 2 · Greetings join their scenario

Each `SCENARIOS` entry gains a `greeting`, lifted verbatim from `ChatTab`'s
`intros`:

```js
{
  id: 'coffee',
  name: 'Order Coffee',
  icon: '☕',
  desc: 'at a Berlin café',
  greeting: {
    de: 'Willkommen im Café! Was möchten Sie bestellen?',
    ipa: '[vɪlˈkɔmən ɪm kaˈfeː vas ˈmœçtən ziː bəˈʃtɛlən]',
    en: 'Welcome to the café! What would you like to order?',
  },
}
```

`ChatTab` looks the scenario up by id and reads its `greeting`; the local
`intros` object is deleted. The file already does this lookup elsewhere — line
122 resolves the same scenario for its `desc` — so the pattern is not new.

**Why nested rather than a `CHAT_GREETINGS` map.** A parallel map keyed by
scenario id is a second structure that must agree with the first. Today's code
does `intros[scenario]` with no fallback, so a pack that adds a fifth scenario
gets `undefined` and crashes on `.de` — a runtime error from a data omission
nothing checks. Nesting makes a scenario without a greeting impossible to
express, and `validate.js` enforces the shape at startup.

---

## 3 · Special letters become a flag

`AlphabetTab.jsx:325` hardcodes `['Ä','Ö','Ü','ß']` to tint those keys in the
letter grid. They are the last four `ALPHABET` entries (lines 28-31), so each
gains `special: true`:

```js
{ l: 'Ä', w: 'Äpfel', e: 'apples', special: true },
```

and the component reads `letter.special`. Entries without the flag are
ordinary — the field is optional, and absent means `false`.

A separate list would be one more thing to keep in sync with the alphabet it
describes; the flag cannot drift from the letter it is attached to.

---

## 4 · Article position

`resolve.js:8` currently assumes the article precedes the noun. `pack.grammar`
gains:

```js
articlePosition: 'before',   // 'before' | 'after'
```

and `resolveCard` composes accordingly. This is the last item Phase 1.4
deferred, and it carries a signature tail like 1.4's did:

| Function | Change |
|---|---|
| `resolveCard(entry)` | `resolveCard(entry, grammar)` |
| `resolveDecks(decks, lexicon)` | `resolveDecks(decks, lexicon, grammar)` |
| `resolveAutoDeck(…)` in `lexiconStore.js` | takes `grammar` |

`de/index.js` passes its own `grammar`; `VocabTab.jsx` passes
`activePack.grammar` to `resolveAutoDeck`, which it can do because it already
imports `activePack`.

**No `activePack` import inside `lexiconStore.js`.** Threading the argument
keeps the engine modules pure, exactly as Phase 1.4 chose for `formatVerb`.
It also sidesteps an import question: `lexiconStore` is engine code and
`activePack` reaches it only through `packs/index.js → de/index.js`. Verified
there is no cycle today — `de/autoDecks.js` only mentions `lexiconStore` in a
comment — but threading avoids creating the possibility.

## 5 · Validation

`validateLanguagePack` gains:

- every entry in `content.scenarios` has a `greeting` object with non-empty
  `de`, `ipa` and `en` strings
- `grammar.articlePosition` is `'before'` or `'after'`

Failures throw at startup naming the field, as every other contract violation
does. No runtime fallback.

The scenario-greeting rule is the one that earns its place: without it, a
missing greeting is a `TypeError` inside a `useEffect` on scenario change —
far from the omission that caused it.

---

## 6 · What this phase does not do

**Category C — chrome and gamification naming (~25 strings).** Deferred to its
own spec, because it needs a product decision this phase should not make:

- `src/lib/gamification.js` — `RANKS` (`Anfänger`, `Lernende`,
  `Fortgeschritten`, `Sehr gut`, `Fließend`, `Muttersprachler`) and
  `ACHIEVEMENTS` names (`Drei am Stück`, `Wochenheld`, `Zwei Wochen`,
  `Monatsmeister`, `Erste Hundert`, `Fünfhundert`, `Tausend`, `Wortschatz 25`)
- `src/App.jsx` — toast copy: `Tagesziel erreicht!`, `Freeze genutzt`,
  `Streak gerettet`, `Neuer Rekord!`, `Meilenstein`, `Liga gewonnen!`,
  `Liga-Meister`
- `chat/WelcomeBanner.jsx` `WILLKOMMEN`, `chat/MessageBubble.jsx` `DU`,
  `chat/MessageList.jsx` `tippt`, `chat/CorrectionPanel.jsx` `Alles gut!`,
  `TranslateTab.jsx` `title="Übersetzen"`

The question that spec must answer: **is the German flavour the product's
brand, or is it language content?** If brand, C stays and a Spanish pack
inherits German chrome by design. If content, C moves behind the pack and the
app loses a piece of its character. Neither answer is obviously right, which
is exactly why it does not belong in a file-move phase.

**`src/lib/stats.js:23`** still holds `LEVELS = ['a1','a2','b1']`, the last
hardcoded level list. Not content, so out of scope here too — carried forward
from Phase 1.4's §6.

## 8 · Testing

**No behaviour changes anywhere.** Every component test must pass unmodified —
`AlphabetTab.test.jsx` in particular, since the special-letter tint moves from
a hardcoded list to a data flag and must render identically.

Test churn in `src/packs/` is expected: the four new test files are
`content.test.js` redistributed, and `resolve.test.js` / `lexiconStore.test.js`
change because `resolveCard` gains a parameter (the same inherent churn Phase
1.4 had, for the same reason).

**New coverage:**

- `scenarios.test.js` — every scenario has a greeting with non-empty `de`,
  `ipa`, `en`; the ids still match what `CHAT_TASKS` keys on.
- `alphabet.test.js` — exactly the four expected entries carry `special: true`,
  and every entry still has `l` / `w` / `e`.
- `validate.js` rejections — a scenario missing `greeting`; a greeting missing
  `ipa`; `articlePosition` set to something other than `'before'` / `'after'`.
- `resolve.test.js` — `articlePosition: 'after'` produces `Brot das`, proving
  the composition is pack-driven rather than merely relocated. This is the
  counterpart of Phase 1.4's French `formatVerb` fixture.

**Known coverage gap:** `ChatTab` has no test file, so nothing exercises it
actually rendering a greeting. `scenarios.test.js` asserts the data and
`validate.js` requires it, but the wiring itself is unverified. Stated so it is
not mistaken for coverage that exists.

## 9 · Risks

| Risk | Mitigation |
|---|---|
| A greeting is lost or altered in the move | Lift verbatim; `scenarios.test.js` asserts all four are present and non-empty |
| The special-letter tint changes | `AlphabetTab.test.jsx` must pass unmodified (§8) |
| `articlePosition` threading creates an import cycle | Grammar is threaded as an argument, never imported into `lexiconStore` (§4) |
| Category C looks forgotten | Enumerated in §6 with the open product question named |

---

## 10 · Success criteria

1. `src/data/` no longer exists; every piece of German content lives under
   `src/packs/de/`.
2. `ChatTab` holds no German; greetings come from the scenario.
3. `AlphabetTab` holds no German; special letters come from the data.
4. `resolve.js` composes the noun display form from `grammar.articlePosition`,
   proven by an `'after'` test.
5. Every component test passes unmodified.
6. The only German left outside the pack is category C, enumerated in §6 —
   **after which Phase 3 is unblocked.**
