# Backend B1 — The Supabase Data Lane (Schema, RLS, Durable Rate Limiting)

**Date:** 2026-06-12
**Status:** Approved design (brainstormed and user-approved in session).
**Relationship:** Executes phase **B1** of
`2026-06-10-backend-architecture-design.md` (the umbrella spec). B0 — the
versioned AI lane — shipped 2026-06-11 (PR #17) and left two explicit slots
this phase fills: the durable rate-limit store and the database half of the
developer interface. Client-side work (anonymous identity, sync) is **B2**,
not here.

---

## Decision summary

| Decision | Choice | Rationale |
|---|---|---|
| RLS test strategy | Vitest + `supabase-js` against the local stack (`supabase start`), behind `npm run test:rls` | Exercises the real attack path (auth → PostgREST → RLS), same runner/idiom as the rest of the repo; `npm test` stays Docker-free. pgTAP rejected: tests below the API layer, second idiom. |
| Atomic rate counter | One Postgres function via RPC (`INSERT … ON CONFLICT … RETURNING`) | Single round-trip, race-free under concurrent function instances. JS-side read-modify-write rejected: racy. |
| Missing Supabase env | Fall back to B0's `MemoryStore` + one-time warning | Code can merge before the cloud project exists; an outage can't take the AI lane down. |
| Store-call failure | **Fail open** (allow request, log error) | AI-lane availability outranks limiter strictness; B0's input caps still bound damage. |
| `updated_at` | Set by the writer; `default now()`; **no server trigger** | B2's last-write-wins merge compares writer timestamps; a server trigger would overwrite them. |
| Performance | One ~20–50ms RPC (EU) per AI call; zero client-bundle change | Hidden inside multi-second Claude calls; RLS checks are PK index hits. |

## Deviation from the umbrella spec (deliberate, flagged)

Two flagged deltas, both in `srs_state`, both because the umbrella's column
list was illustrative while this spec finalizes against the shipped engine:

1. **Leitner shape, not generic SRS.** The umbrella sketched
   `due_at, interval, ease, lapses`; the real engine (`src/lib/srs.js`) is a
   Leitner scheduler storing `{ box, lastReviewed, nextDue, reps }`. B1
   mirrors reality so B2 syncs with no translation layer.
2. **`srs_key`, not `card_id`.** The engine's storage unit is the composite
   key `'<deckId>:<cardId>'`; B1 stores it verbatim in one column and names
   the column for what it holds.

## Scope

**In:** `supabase/` directory (CLI config + versioned migrations), six tables
with RLS, profiles auto-create trigger, `increment_rate_limit` SQL function,
`SupabaseStore` + service-role client in `api/_lib/`, the adversarial RLS
suite + `npm run test:rls`, a second CI job, `docs/api/data.md`, two new
server-only env vars.

**Out (deferred):** browser-side `supabase-js`, anonymous identity and account
linking (B2/B3), the sync engine (B2), user-id rate-limit keys (B2 — the key
fn gains a JWT branch then), export/delete endpoints (B3), seed data (tests
create their own users; no `seed.sql`).

**Invariant:** zero app-behavior change. The only runtime difference is where
rate-limit counters live. `npm test` (327) and the pre-commit hook are
untouched and never require Docker.

## Schema (migration 2 — user tables)

All user tables: `pack_id text not null default 'de'` from day one (umbrella
interlock with platform Phase 4); FK to `auth.users` with `on delete cascade`;
RLS enabled in the same migration.

```sql
create table public.profiles (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  display_name text,
  created_at timestamptz not null default now()
);

create table public.srs_state (
  user_id       uuid not null references auth.users(id) on delete cascade,
  pack_id       text not null default 'de',
  srs_key       text not null,  -- the engine's full key, verbatim: '<deckId>:<cardId>'
  box           smallint not null default 1 check (box between 1 and 5),
  last_reviewed timestamptz,
  next_due      timestamptz,
  reps          integer not null default 0,
  updated_at    timestamptz not null default now(),
  primary key (user_id, pack_id, srs_key)
);

create table public.stats_daily (
  user_id    uuid not null references auth.users(id) on delete cascade,
  pack_id    text not null default 'de',
  day        date not null,
  counters   jsonb not null default '{}',
  updated_at timestamptz not null default now(),
  primary key (user_id, pack_id, day)
);

create table public.decks (
  user_id    uuid not null references auth.users(id) on delete cascade,
  pack_id    text not null default 'de',
  deck_id    text not null,
  name       text not null,
  cards      jsonb not null default '[]',
  updated_at timestamptz not null default now(),
  primary key (user_id, pack_id, deck_id)
);

create table public.settings (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  data       jsonb not null default '{}',
  updated_at timestamptz not null default now()
);
```

**Column ↔ localStorage mapping (for B2):** one `srs_state` row ↔ one
`srs['<deckId>:<cardId>']` entry, with `srs_key` holding that key **verbatim**;
`stats_daily.counters` ↔ the `daily['YYYY-MM-DD']` object; `decks.cards` ↔
custom-deck card arrays; `settings.data` ↔ the `gamification` key.

> **Note on SRS keys:** the engine's SRS identity unit is the composite
> `srsKey(deckId, cardId)` = `'greetings:Hallo'`. B1 stores it whole rather
> than split into columns: byte-equality makes B2's sync a key-for-key copy
> with zero parsing (German card ids may in principle contain `:`), and the
> engine never queries by deck on the server. Honest naming follows —
> `srs_key`, not `card_id` (second deviation, see the deviation log).

**Profiles auto-create (canonical Supabase pattern):**

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer set search_path = ''
as $$
begin
  insert into public.profiles (user_id) values (new.id);
  return new;
end $$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

### RLS policies

Per user table (shown for `srs_state`; identical for `stats_daily`, `decks`,
`settings`):

```sql
alter table public.srs_state enable row level security;

create policy "select own rows" on public.srs_state
  for select using (auth.uid() = user_id);
create policy "insert own rows" on public.srs_state
  for insert with check (auth.uid() = user_id);
create policy "update own rows" on public.srs_state
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "delete own rows" on public.srs_state
  for delete using (auth.uid() = user_id);
```

`profiles`: select / insert / update own — **no delete policy** (account
deletion is a B3 server-side operation; the FK cascade from `auth.users`
handles it).

## Rate limiting (migration 1 + `api/_lib`)

```sql
create table public.rate_limits (
  key          text not null,
  window_start bigint not null,   -- epoch ms, matches B0's window math
  count        integer not null default 1,
  primary key (key, window_start)
);

alter table public.rate_limits enable row level security;
-- no policies: invisible to anon and authenticated; service role only

create or replace function public.increment_rate_limit(p_key text, p_window_start bigint)
returns integer
language plpgsql
security definer set search_path = ''
as $$
declare new_count integer;
begin
  -- opportunistic cleanup of this key's expired windows (bounded, indexed)
  delete from public.rate_limits
    where key = p_key and window_start < p_window_start;

  insert into public.rate_limits (key, window_start, count)
    values (p_key, p_window_start, 1)
  on conflict (key, window_start)
    do update set count = public.rate_limits.count + 1
  returning count into new_count;

  return new_count;
end $$;

revoke execute on function public.increment_rate_limit(text, bigint) from public;
revoke execute on function public.increment_rate_limit(text, bigint) from anon, authenticated;
grant  execute on function public.increment_rate_limit(text, bigint) to service_role;
```

**`api/_lib/supabase.js`** — service-role client factory; returns `null` when
`SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` are absent (module-cached client,
`persistSession: false`).

**`api/_lib/ratelimit.js` additions:**

```js
export class SupabaseStore {
  constructor(client) { this.client = client; }
  async increment(key, windowStart) {
    const { data, error } = await this.client.rpc('increment_rate_limit', {
      p_key: key,
      p_window_start: windowStart,
    });
    if (error) throw new Error(error.message);
    return data;
  }
}

export function defaultStore() {
  const client = serviceClient();
  if (client) return new SupabaseStore(client);
  warnOnce(); // "rate limiting is per-instance (memory) — SUPABASE_* env not set"
  return new MemoryStore();
}
```

`createRateLimiter` gains a fail-open guard: a thrown `store.increment` is
caught, logged (`console.error`), and treated as `{ allowed: true }`.
`createAiHandler` passes `store: defaultStore()` (module-load selection, one
store per function instance). B0's tests keep passing — `MemoryStore` and the
interface are unchanged.

## Adversarial test suite (`npm run test:rls`)

Requires a running local stack; reads `SUPABASE_URL` / `SUPABASE_ANON_KEY` /
`SUPABASE_SERVICE_ROLE_KEY` from env (helpers also accept the CLI's
`API_URL` / `ANON_KEY` / `SERVICE_ROLE_KEY` names, so `eval "$(supabase
status -o env)"` works directly). Setup: admin client creates users A and B;
each gets a signed-in anon-key client.

Per user table, authenticated as A:
1. Insert own row → succeeds.
2. Select B's rows → **zero rows** (not an error — RLS filters silently).
3. Insert a row with `user_id = B` → **rejected** (`with check` violation).
4. Update / delete B's row → **zero rows affected**.

Plus: bare-anon select on every table → zero rows / denied; `rate_limits`
select as A → zero rows; `increment_rate_limit` RPC as A → **permission
denied**; RPC as service role → returns 1, 2, 3 on successive calls in one
window and resets in the next; counts are independent per key.

Any cross-user success **fails the build**.

## CI

```yaml
rls-policy-tests:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with: { node-version-file: '.nvmrc' }
    - run: npm ci --legacy-peer-deps
    - uses: supabase/setup-cli@v1
      with: { version: latest }

    - run: |
        eval "$(supabase status -o env)"
        export SUPABASE_URL="${SUPABASE_URL:-$API_URL}"

        export SUPABASE_SERVICE_ROLE_KEY="${SUPABASE_SERVICE_ROLE_KEY:-$SERVICE_ROLE_KEY}"

```

`supabase start` succeeding is itself the migration-validity gate.

## Rollout (safe order by construction)

1. **Merge + deploy first** — fallback store keeps prod identical to today.
2. **Owner runbook** (agent prompts at execution): start Docker Desktop;
   `brew install supabase/tap/supabase`; create the free Supabase project
   (EU — Frankfurt), flip on **anonymous sign-ins** while in the dashboard
   (needed at B2, free now); `supabase link --project-ref <ref>`;
   `supabase db push`; add the two env vars to Vercel; redeploy.
3. **Verify:** CI suite green; the B0 production battery still 6/6;
   `rate_limits` rows accruing after a few prod AI calls
   (`select * from rate_limits` in the dashboard / via CLI).

**Done when:** all of step 3 holds and `npm test` still passes 327 with no
Docker anywhere in its path.
