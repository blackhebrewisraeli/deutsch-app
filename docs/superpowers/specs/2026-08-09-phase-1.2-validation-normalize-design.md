- **Date:** 2026-08-09
- **Status:** Approved
- **Author:** Claude Code (brainstormed with Semion)
- **Parent:** `2026-06-09-languagepack-contract-design.md` (the LanguagePack
  contract), `2026-06-09-multi-language-platform-design.md` (the phase plan)

  Phase 1.1 (shipped — card identity re-key)
- **Blocks:** Phase 3 (second language pack)

---

## Scope

Phase 1.2 moves text normalization from a single opaque pack function to a
declarative, two-sided contract: the **engine** owns how English answers are
compared, the **pack** owns how its own language is compared.

This is a refactor phase. **It changes no observable behaviour** — §7 makes
that an assertion, not an aspiration.

Out of scope: any new practice surface (including a reverse "type the German"
vocab mode), `TypingExercise`'s Claude grader (Phase 1.3, `pack.prompts`),
`cardId` / `srsKey`, and every content change.

---

## Why

### The queued description was wrong, and the correction is the design

The Tier B queue described Phase 1.2 as "`validation.normalize` diacritics
handling (ß/ä/ö/ü answer matching through the pack)". Exploration found that
**ß/ä/ö/ü cannot currently reach `normalize` from anything a user types.**

Every call site, as of `main` @ `cbbbbfe`:

| Call site | Expected side | User input | Typed? |
|---|---|---|---|
| `VocabTab.submitTyped` | `card.en` — **English** | "Type the English meaning…" | yes, **English** |
| `TileExercise.check` | German sentence | tapped tiles | **no** |
| `BlankExercise.check` | German blanks | tapped tiles | **no** |

The one surface where a learner types German — `TypingExercise` (B1) — is
graded by Claude and never calls `normalize`. `AlphabetTab` is multiple
choice, `ChatTab` is AI conversation, and no surface searches the lexicon by
text (deck filters key on tag / CEFR / frequency rank).

So the German pack's `normalize` — `(s) => s.trim().toLowerCase()` — is today
applied **almost entirely to English text**. That is the actual defect: a
pack-level concern governing text the pack has nothing to do with. A French
pack added in Phase 3 would inherit the power to change how English answers
are matched, and two packs would silently disagree about it.

### The trap in the obvious fix — and why it is smaller than it looks

Making a *single shared* `normalize` fold `ß→ss` would have introduced a bug.
The tile exercises compare app-supplied strings drawn from
`exercise.words ∪ exercise.distractors`; a word `Fuß` beside a distractor
`Fuss` would have normalized identically, and **placing the wrong tile would
grade as correct**.

The two-sided split defuses this on its own. Tile comparisons use an
*engine* rule set, and no engine set carries `replacements` — a pack's
substitutions never reach them. The collision is impossible whatever any pack
declares, without needing tiles to be strict.

> **Amended during implementation.** This spec originally had tiles use a
> `STRICT` (trim-only) set, reasoning that tapped tiles carry no input
> variance to forgive. That reasoning was wrong: `BlankExercise` deliberately
> accepts a capitalised distractor for a lower-case answer — clicking `Bin`
> when the blank wants `bin` is correct, pinned by a test since PR #27.
> Making tiles strict broke it. The set is now `CHOICE` (trim + case-fold),
> byte-identical to today's behaviour, and the collision argument above is
> what actually keeps `Fuß`/`Fuss` apart.

## Decisions

| # | Decision | Choice |
|---|---|---|
| 1 | What Phase 1.2 is | **Pack-owned text policy** — architectural. Not a new typed-German surface, and not a re-scope to today's small matching bugs |
| 2 | Ownership | **Split.** Engine owns answer-language (English) rules; the pack owns only its own target language |
| 3 | Contract shape | **Declarative rules**, applied by the engine. Not a function, and no function escape hatch |
| 4 | German policy | **Keyboard substitutions only** — `ß→ss`, `ä→ae`, `ö→oe`, `ü→ue`. No stripping of combining marks |
| 5 | Tile comparisons | **`CHOICE` — trim + case-fold, no substitutions.** Byte-identical to today. Amended during implementation; see the note below |

Decision 3 rejects an escape-hatch function deliberately: two code paths from
day one, and the escape hatch becomes the default.

Decision 4 draws the line at what German orthography itself defines for
keyboards lacking the characters. Stripping marks to bare vowels would
collapse real word pairs — `schön`/`schon`, `Bär`/`Bar`, `Würde`/`Wurde` —
so wrong answers would grade as correct.

## 1 · The contract

`pack.validation.normalize` (function) is **removed** and replaced by
`pack.validation.target` (data):

```js
// src/packs/de/index.js
validation: {
  target: {
    trim: true,
    caseFold: true,
    stripCombiningMarks: false,   // keeps schön ≠ schon
    replacements: [
      ['ß', 'ss'],
      ['ä', 'ae'],
      ['ö', 'oe'],
      ['ü', 'ue'],
    ],
  },
}
```

Every field is required — no defaulting. A pack that means "no folding"
writes `replacements: []`, which is a statement rather than an omission.

### Why data rather than a function

- `validate.js` can check the **shape**. Today it can only assert
  `typeof === 'function'`, which passes for `() => ''`.
- The rules are unit-testable per pack without going through a consumer.
- They are inspectable in review — the `Fuß`/`Fuss` class of trap is visible
  in a diff instead of hidden in a closure.
- They serialize. Phase 4 contemplates packs being *selected* rather than
  imported; a function cannot cross that boundary.

---

## 2 · The pipeline

New module `src/lib/textRules.js` owns the algorithm:

```js
export function normalizeText(s, rules) → string
```

Operations apply in a **fixed, contractual order**:

```
trim → caseFold → stripCombiningMarks → replacements
```

The order is load-bearing, not incidental. Case-folding before replacement is
why `ÄRGER` reaches `aerger` while the pack lists only lowercase pairs — the
alternative is every pack declaring both cases of every pair and one of them
eventually going missing.

**`caseFold` means `toLowerCase()`, not Unicode full case-folding.** This
distinction matters for exactly this language: full folding already maps
`ß→ss` internally, which would silently pre-empt the pack's own declaration
and make `replacements` look inert for the one pair it most obviously
governs. Lowercasing keeps every substitution the pack's to state.

`stripCombiningMarks` is NFD-decompose, drop `\p{M}`, NFC-recompose. It is
`false` for German and exists for packs whose scripts need it (Hebrew niqqud,
Arabic tashkeel), so those packs do not need an escape hatch.

`replacements` apply in declared order, each globally.

Non-string input returns `''` rather than throwing — a normalizer is called
on user input in a render path and must not be able to blank the screen.

## 3 · The three rule sets

`textRules.js` also exports the two the **engine** owns:

| Set | Owner | Applied to | Rules |
|---|---|---|---|
| `CHOICE` | engine | tapped tiles / blanks | `trim` + `caseFold` |
| `ANSWER` | engine | typed English answers | `trim` + `caseFold` |
| `validation.target` | pack | typed target language | pack's declaration |

`CHOICE` and `ANSWER` hold the same values today and are still two names: they
answer to different questions. `ANSWER` may gain rules if English matching
ever needs them; `CHOICE` should stay minimal, and crucially must never carry
`replacements`.

`ANSWER` reproduces today's `(s) => s.trim().toLowerCase()` exactly. English
is the UI language and is shared by every pack, so one definition serves all
of them.

**Phase 4 note.** `ANSWER` assumes the answer language is English. If Phase 4
ever lets someone learn German *from* Hebrew, that assumption breaks and
`ANSWER` becomes a property of the UI locale rather than a constant. This
spec does not solve that — it records where the seam will be.

## 4 · Call-site changes

`matching.js` takes rules instead of a function, defaulting to the safe set:

```js
export function exactMatch(expected, given, rules = CHOICE)
export function fuzzyMatch(expected, given, rules = ANSWER, maxDistance = 2)
```

| Consumer | Before | After |
|---|---|---|
| `VocabTab.submitTyped` | `activePack.validation.normalize` | `ANSWER` |
| `TileExercise.check` | `activePack.validation.normalize` | `CHOICE` (the default) |
| `BlankExercise.check` | `activePack.validation.normalize` | `CHOICE` (the default) |
| *(none yet)* | — | `activePack.validation.target` |

### Tiles keep folding case

Tile comparisons keep exactly the behaviour they have today. `BlankExercise`
offers capitalised distractors for lower-case answers on purpose and treats
them as correct — capitalisation is not what those exercises test — and a
test has pinned that since PR #27.

What changes is only *who owns* the rule: an engine set rather than the
German pack's function. Because no engine set carries `replacements`, a
pack's `ß→ss` can never reach a tile, so the `Fuß`/`Fuss` collision stays
impossible without making tiles strict.

### `validation.target` ships with no consumer

This is intentional and worth stating plainly: Phase 1.2 delivers the
contract, the German declaration, and the tests. The first consumer will be
whichever surface first accepts typed target-language input. Shipping the
rules now is what lets that surface be additive rather than another contract
change.

## 5 · Validation and failure

`validateLanguagePack` gains a real check on `validation.target`:

- `target` is an object; `trim`, `caseFold`, `stripCombiningMarks` are
  booleans; `replacements` is an array
- every replacement is a two-element array of strings
- the `from` side is non-empty (an empty `from` makes replacement divergent)

Failures throw at startup naming the offending field, exactly as the existing
contract violations do. **There is no runtime fallback.** A pack whose text
rules are malformed should fail to boot, not silently mis-grade answers.

## 7 · Testing

**The load-bearing assertion: every existing consumer test passes untouched.**
This is a refactor; if `VocabTab.test.jsx`, `TileExercise.test.jsx` or
`BlankExercise.test.jsx` needs editing to stay green, behaviour changed and
the change is a bug until proven otherwise. (`matching.test.js` is the one
exception — it passes a `norm` function today and must move to rule sets.)

**`textRules`** — each flag in isolation; pipeline order (`ÄRGER` → `aerger`
proves caseFold precedes replacement); `replacements: []` is identity beyond
trim/case; non-string input returns `''`.

**German rules, positive** — `groß`↔`gross`, `Fuß`↔`Fuss`, `Straße`↔`strasse`,
`ÄRGER`→`aerger`, `Tschüß`↔`tschuess`.

**German rules, negative** — these must NOT match, and are the reason
Decision 4 rejects mark-stripping:

| a | b | a normalizes to | b normalizes to |
|---|---|---|---|
| `schön` | `schon` | `schoen` | `schon` |
| `Bär` | `Bar` | `baer` | `bar` |
| `Würde` | `Wurde` | `wuerde` | `wurde` |

**One accepted collision.** `Maße` and `Masse` are distinct words that
`ß→ss` collapses — both normalize to `masse`, so the pack will accept either
for the other. This is the known cost of Decision 4, not an oversight: a
learner on a US keyboard cannot type `Maße` at all, and refusing every `ss`
spelling to protect one rare pair costs more than it saves. Pin it as a test
asserting they DO match, so the trade-off is visible in the suite rather than
rediscovered as a bug report.

**`validate.js`** — missing `target`; non-boolean flag; `replacements` not an
array; a replacement that is not a two-string pair; empty `from`.

## 8 · Risks

| Risk | Mitigation |
|---|---|
| A future pack wants folding the schema cannot express | `stripCombiningMarks` covers the common scripts. If one genuinely cannot be expressed, extend the schema — do not add an escape hatch (Decision 3) |
| `Maße`/`Masse` collapse | Accepted and documented above |
| `ANSWER` assumes English | §3 records the seam for Phase 4 |
| A pack's substitutions reach a tile and collide two options | No engine set carries `replacements`, and tiles only ever use an engine set. Pinned by a test asserting `Fuß` ≠ `Fuss` under `CHOICE` |

---

## 9 · Success criteria

1. No pack supplies a function for text handling; `validate.js` enforces the
   rules shape.
2. English answer matching is engine-owned and identical to today.
3. The German pack declares keyboard-substitution folding, with the negative
   cases pinned by tests.
4. Every existing consumer test passes unmodified.
5. A second pack can declare its own text rules without touching engine code
   or English matching — the Phase 3 unblock.
