# Backend B2.2 — Sync engine (design)

**Date:** 2026-06-19
**Status:** Approved design (brainstormed and user-approved in session).
**Parent:** `2026-06-13-backend-b2-auth-sync-design.md` (the B2 milestone). This
sub-spec finalizes the sync engine that B2.1 (the auth surface, merged via
PR #38) was built to feed.
**Depends on:** B1 (the five user tables + RLS + explicit grants, live in
production) and B2.1 (`src/lib/auth.js` + `useAuth()`, merged).

---

## Problem

B2.1 shipped the auth surface — a user can sign in, and `useAuth()` exposes the
session — but nothing yet moves local progress to Supabase or back. B2.2 builds
`src/lib/sync.js`: the engine that pushes local writes up when a session exists,
pulls on sign-in / resume, and **merges** a guest's local progress into an
account on first sign-in. `localStorage` stays the offline source of truth; the
whole engine is behind a `VITE_SYNC_ENABLED` flag and is a complete no-op when
signed out, offline, or flag-off.

---

## Decisions locked in brainstorming

| Decision | Choice |
|---|---|
| `stats_daily` merge | **Additive** — counters are summed across devices, not last-write-wins (LWW on cumulative counters silently drops a device's same-day activity, which would corrupt XP/streak/goal). |
| Additive idempotency | **Delta sync** — push the change since last sync, not the whole local value, so re-syncing a day never double-counts. |
| `srs_state` merge | **LWW by the existing `lastReviewed`** field (the parent spec's "prefer the more recent review") — no new timestamp needed. |
| `decks` / `settings` / `profile` merge | **LWW by an `updatedAt`** stamped on change (the only new stamps B2.2 adds). |
| Conflict UI | **None** — the per-record rules are the policy. |
| Flag | `VITE_SYNC_ENABLED` (build-time). Off → app byte-identical to today. |

---

## Architecture

```
                     localStorage (deutsch-app-state-v1)  ← offline source of truth, keys untouched
                              │  ▲
                  toRows()    │  │  fromRows() / merge
                              ▼  │
   src/lib/sync.js  ──  per-store adapters  ──►  Supabase (5 B1 tables, RLS: user_id = auth.uid())
        │  debounced push (~3s) when a session exists
        │  pull on sign-in + on visibilitychange resume
        └  first sync after sign-in = the merge (pull → merge → push)
   uses useAuth()/getClient() from src/lib/auth.js (the only Supabase entry point)
```

`sync.js` is language-blind (no German, no pack imports) and imports the
session/client only through `src/lib/auth.js`. Each store gets a small,
independently-testable adapter; `sync.js` orchestrates them.

## Storage shape → tables (adapter map)

Current local blob (single key `deutsch-app-state-v1`, via `loadState`/`saveState`):

```
{ stats, learnedWords, daily, items, srs, gamification, <custom decks> }
```

| Local slice | → Table | Key | Merge |
|---|---|---|---|
| `srs` map `'<deckId>:<cardId>' → { box, lastReviewed, nextDue, reps }` | `srs_state` | `srs_key` = the composite key verbatim (B1 stores it as-is) | LWW by `lastReviewed` (newer review wins; null `lastReviewed` loses to any real one; exact tie → server) |
| `daily` map `'YYYY-MM-DD' → counters` | `stats_daily` | `day` | **Additive (delta sync)** — see below |
| custom user-created decks | `decks` | `deck_id` | LWW by `updatedAt` |
| settings slice (`level`, `gamification.goal`/`soundOn`/`achievements`/`lastGoalMet`, `learnedWords`) | `settings.data` (single jsonb row) | `user_id` | LWW by `updatedAt` |
| display name | `profiles.display_name` | `user_id` | LWW by `updatedAt` |

`items` (the review-feed wrong-answer log) is local-only and **not synced** —
the B1 schema's five tables deliberately don't include it; on a new device the
review feed simply rebuilds from new activity. `stats.streak`/`learnedCount` are
**derived** (from synced `daily` / `learnedWords`) and recompute locally, so
they aren't synced directly either. Preset decks are content, never synced.
Exact field-name mappings (especially the `settings.data` shape and where custom
decks live in the blob) are finalized in the implementation plan.

## The additive-stats mechanism (delta sync)

Plain summing is not idempotent: re-syncing a day, or signing out and back in,
would double-count. So the stats adapter tracks a per-day **`lastSyncedCounters`
snapshot** (in a new local key `deutsch-app-sync-meta-v1` — additive, not a
rename of any existing key):

- **Push:** for each dirty day, `server_counters += (local_counters − lastSynced)`;
  then set `lastSynced = local_counters`. Pushing the *delta* means a repeated
  push of an unchanged day is a no-op.
- **Pull:** adopt the server counters into local, and set `lastSynced = server_counters`
  so the next push delta is measured from the reconciled baseline.
- **First-sign-in merge:** the guest's local days have `lastSynced = 0` (never
  synced), so the whole local value is the delta and is added to the account —
  guest progress survives sign-up, exactly once.

Counters are summed key-by-key inside the `counters` jsonb (`total`, `byTab.*`,
`byLevel.*.{correct,almost,wrong}`), so partial overlap across devices merges
correctly. XP/streak/goal derive from the merged `daily` locally — the
derivation code is untouched.

---

## `updatedAt` stamping (minimal, additive)

Only the LWW-by-`updatedAt` records need a new stamp; B2.2 adds it at the few
mutation points:
- **decks:** stamp `updatedAt = Date.now()` when a custom deck is created/edited.
- **settings:** stamp a single `settingsUpdatedAt` when any synced setting changes.
- **profile:** stamp `updatedAt` when the display name changes.

`srs_state` reuses the existing `lastReviewed`; `stats_daily` is additive and
needs no LWW stamp. No existing storage key is renamed or namespaced (the
Phase-4 constraint holds). The `profiles` table has no `updated_at` column today
— whether to add one via a one-column migration or carry the profile stamp in
the client/`settings` blob is settled in the plan.

## Triggers & lifecycle

- **Outbound:** a ~3-second debounced push of dirty records whenever a session
  exists. Dirty-tracking is per record (a small in-memory set + the sync-meta
  snapshot for stats).
- **Inbound:** pull on `useAuth()` reaching `authenticated`, and on
  `visibilitychange` → visible (resume).
- **First sync after sign-in = the merge:** pull → merge per the rules above →
  push. This is the guest-progress-survives-signup path and the cross-device
  reconcile path; they are the same code.
- **Signed out / offline / flag-off:** the engine never initializes — no
  listeners, no writes; the app behaves byte-identically to today.

---

## Sync-status UI (minimal)

- **AccountChip:** the pending-sync dot the B2.1 chip reserved space for —
  shown while a push is queued or in flight.
- **Stats Account section:** a "last synced ·  <relative time>" line when signed
  in. No conflict UI.

These are the only B2.2 component changes; they consume sync state exposed by
`sync.js` (e.g. a small `useSyncStatus()` hook or a subscription).

## Edge cases

| Case | Handling |
|---|---|
| Sign in offline, then connectivity returns | Push is queued; fires when a session + network are available. No data loss (local is source of truth). |
| Same day practiced on two devices | Additive delta sync sums both contributions; neither is lost. |
| Sign out then back in on the same device | `lastSynced` snapshot makes the re-merge a no-op for already-synced data; only new local activity is pushed. |
| Clock skew between devices | LWW uses client clocks (documented limitation; single-user scale). Additive stats are immune (they sum, not compare). |
| Partial/failed push | Retried on the next debounce/trigger; dirty set persists until a record is confirmed pushed. |
| Conflicting deck/settings edits across devices | LWW by `updatedAt` — newest wins, by policy. |

## Testing

- **Merge rules** (the heart) — pure functions, table-driven unit tests: LWW
  ordering, srs `lastReviewed` preference (incl. null), additive delta
  idempotency (push twice → counted once), first-sign-in merge, empty/partial
  sides, clock-tie → server.
- **Adapters** — round-trip tests (`fromRows(toRows(x)) ≅ x`) per store.
- **Engine** — `sync.js` against a mocked supabase client (no network): debounce
  coalescing, pull-on-resume, no-op when signed out / flag-off.
- **Authorization** — already covered by the 30-test adversarial RLS suite; no
  new DB tests.
- **Manual** (in the plan): two-device merge; guest-progress-survives-signup;
  flag-off = app unchanged.

## Rollout

One PR stage, behind `VITE_SYNC_ENABLED` (off in CI/prod until the manual
two-device verification passes). Division per AGENTS.md: Claude Code owns the
merge engine, the delta-sync logic, and `sync.js`; Cursor can take the
pure-function merge-rule tests and the adapter round-trip tests as well-scoped
missions.

**Success criteria:**
- A fresh device restores progress within seconds of sign-in.
- Guest progress made before sign-up survives the first sync, exactly once
  (no double-count on re-sync).
- Same-day multi-device practice sums correctly; XP/streak/goal stay right.
- Signed-out / flag-off experience is byte-identical to today.
- `npm test` and the RLS suite stay green.
