## Scope

Every AI prompt in the app is hardcoded German. Phase 1.3 splits each one in
two: the **engine** owns the JSON output contract and the framing prose, the
**pack** owns its language, persona and per-level pedagogy.

Out of scope: `pack.grammar` (Phase 1.4), the hardcoded German chat greeting
and the `content.js` chat tasks that name Anna (both are pack *content*,
Phase 1.5), and the server-side AI lane — see §Why, it is already
language-blind.

---

## Why

### There are four prompts, not three

The Tier B queue listed "Anna system prompt, B1 grader, deck generator".
Exploration found a fourth: `src/components/translate/generateSentences.js:12`
generates translation exercises for all three levels and is exactly as
German-specific as the others. It was missed because it lives in a `.js` file
under `src/components/`, where prompt-hunting greps for `.jsx` do not reach.

All four, as of `main` @ `895ecbd`:

| Site | Language-specific part | Engine-contract part |
|---|---|---|
| `ChatTab.jsx:135` | persona `Anna`, "German tutor", per-level pedagogy | strict-JSON `{de, ipa, en, correction, taskComplete}` |
| `TypingExercise.jsx:32` | "German language grader", EN→DE direction | `{verdict, corrected, message}` + the three verdict rules |
| `VocabTab.jsx:194` | "German flashcards", `der Hund`, `[deːɐ̯ hʊnt]` | `{de, en, ipa}` card shape |
| `generateSentences.js:12` | per-level German grammar focus | three exercise shapes (`words` / `blanks` / plain) |

### The server lane is already language-blind

`api/v1/ai/{chat,grade,deck}.js` and `api/_lib/validate.js` check types and
sizes only — `MAX_TOTAL_CHARS`, `system` must be a string — and contain no
German. **Phase 1.3 is a client-only change.** No API contract work, no
migration, no new endpoint.

### `pack.prompts` is an unvalidated placeholder

`src/packs/de/index.js:66` declares `prompts: {}` and `validate.js` never
looks at it — the same state `validation.target` was in before Phase 1.2. A
pack can ship with no prompts at all and boot fine.

## Decisions

| # | Decision | Choice |
|---|---|---|
| 1 | The split | **Engine owns the output contract; pack owns the language.** A pack cannot break a component's parser by rewording its prompt |
| 2 | Pack shape | **Structured fields, engine composes the prose.** Not templates with placeholders, not builder functions |
| 3 | Persona reach | **Prompt + the four UI strings that name her.** The German greeting and `content.js` chat tasks stay for Phase 1.5 |
| 4 | Level keys | **Lowercase** (`a1`), matching how components index them — see §3 |

Decision 1 targets a specific failure mode. A pack-authored JSON shape block
that drifts by one field surfaces as a `JSON.parse` throw at runtime, inside a
`catch` that reports "Could not grade — check your connection." Keeping the
contract engine-side makes that class of bug impossible rather than merely
unlikely.

Decision 2 follows Phase 1.2's precedent for the same reasons: validatable,
testable without a consumer, serializable for Phase 4. It also avoids
inventing a placeholder mini-language whose typos fail *silently* — an
unsubstituted `{scenario}` reaches the model as literal text, and the model
will happily act on it.

## 1 · The contract

```js
// src/packs/de/index.js
prompts: {
  persona: 'Anna',
  targetLanguage: 'German',

  // Chat pedagogy — how the tutor should speak at each level.
  levels: {
    a1: 'The learner is A1 BEGINNER. Use very simple German, short sentences, common vocabulary only. Always provide English translation. Use lots of encouragement.',
    a2: 'The learner is A2 ELEMENTARY. Use natural but simple German. Provide English translation. Gently push them.',
    b1: 'The learner is B1 INTERMEDIATE. Use natural German, moderate complexity. Provide English translation but challenge them.',
  },

  // Exercise generation — what a generated exercise should drill.
  exercises: {
    a1: 'A1 beginner (very simple sentences)',
    a2: 'A2 elementary (focus on articles and prepositions)',
    b1: 'B1 intermediate (complex grammar)',
  },

  // Concrete samples that teach the model the card shape.
  deck: {
    cardExample: 'der Hund',
    ipaExample: '[deːɐ̯ hʊnt]',
  },
}
```

`levels` and `exercises` are both keyed by level and are deliberately
separate. They answer different questions — *how should the tutor talk to
this learner* versus *what should a generated exercise drill* — and the
existing strings already differ in voice and detail. One map serving both
would force each string to hedge between two jobs.

Every field is required. A pack cannot omit `deck.ipaExample` and inherit
German's.

---

## 2 · The engine module

New `src/lib/prompts.js`. It owns every JSON-shape instruction and all
framing prose, and is the only place in `src/` allowed to contain prompt text.

```js
chatSystemPrompt({ prompts, scenarioDesc, task, level }) → string
graderSystemPrompt({ prompts })                          → string
deckPrompts({ prompts, topic })                          → { system, user }
sentencePrompts({ prompts, level })                      → { system, user }
```

The four components stop assembling prompt strings and call these instead.
`ChatTab` keeps building its `history` array and parsing the reply; only the
system-prompt construction moves.

`task` is optional. When absent the engine omits the task sentence entirely
rather than interpolating an empty string — today's code already does this
via `taskLine`, and an empty clause left in a prompt reads to the model as a
task with no content.

---

## 3 · The level-key trap

`meta.cefrLevels` is `['A1', 'A2', 'B1']` (uppercase). `content.translateSentences`
is keyed uppercase to match. But every component branches on lowercase —
`level === 'a1'` — and `level` is threaded down from `App.jsx` state seeded
from `localStorage.getItem('deutsch-level')`, which stores lowercase.

**`prompts.levels` and `prompts.exercises` use lowercase keys**, matching the
value components actually hold. `validate.js` therefore lowercases
`meta.cefrLevels` before checking coverage.

Getting this backwards does not throw. It interpolates `undefined` into the
system prompt as the string `"undefined"`, and the model proceeds on it —
a silent quality regression with no error anywhere. Hence a decision row of
its own, and an explicit validation rule.

---

## 4 · Persona

`prompts.persona` is read by the prompt and by the four UI strings that name
the tutor:

| File | Reference |
|---|---|
| `ChatTab.jsx:243` | "Anna corrects your mistakes…" |
| `chat/WelcomeBanner.jsx:55` | "Anna gives you a task each round…" |
| `chat/MessageBubble.jsx:76` | `aria-label="Play Anna response audio"` |
| `chat/MessageList.jsx:34` | `<span>Anna tippt</span>` |

**Known gap, deliberately not solved here.** `MessageList` becomes
`${persona} tippt` — the *name* is now pack-owned, but `tippt` stays German.
That is UI-chrome localisation, a different problem from persona, and this
phase has no answer for it. Recorded so it is not mistaken for an oversight.

Two references stay hardcoded because they are pack **content**, scheduled
for Phase 1.5:

- `ChatTab.jsx:71-73` — the opening message `'Hallo! Ich bin Anna. Wie heißt du?'`
- `content.js:268+` — chat tasks phrased "Ask Anna how she is."

A pack declaring a different persona will disagree with those two until 1.5.
That is a smaller wrong than pulling content migration into this phase.

---

## 5 · Validation and failure

`validateLanguagePack` gains a `prompts` check:

- `prompts` is an object
- `persona` and `targetLanguage` are non-empty strings
- `levels` and `exercises` are objects with a non-empty string for **every**
  `meta.cefrLevels` entry, lowercased (§3)
- `deck` is an object with non-empty `cardExample` and `ipaExample`

Failures throw at startup naming the field, as every other contract violation
does. **No runtime fallback and no defaulting to German.** A pack with broken
prompts should fail to boot rather than silently teach the wrong language.

## 7 · Testing

**Composition** — each builder includes the pack's fields *and* its contract
block. Assert `chatSystemPrompt` contains the persona, the target language,
the level pedagogy for the level passed, the scenario description, and the
five JSON keys; that it includes the task sentence when `task` is given and
omits it entirely when not.

**The level trap (§3)** — `chatSystemPrompt` with `level: 'a1'` contains the
A1 pedagogy, and **no builder ever emits the literal string `undefined`**.
That last assertion is the one that catches a casing regression.

**Validation** — missing `prompts`; empty `persona`; `levels` missing a
declared CEFR level; a level whose value is an empty string; missing
`deck.ipaExample`.

**Source guard** — `src/noPromptsInComponents.test.js`, in the spirit of
`noHardcodedHex.test.js` and the widened `noTokenAlphaConcat.test.js`: the
strings `You are` and `You generate` may appear under `src/` only in
`src/lib/prompts.js`. Test files are excluded, as in the other two guards —
`prompts.test.js` necessarily contains those strings in its assertions, and
so does the guard itself.

Verified: those two strings currently appear at exactly the four prompt sites
and nowhere else in `src/`, so the guard goes green the moment the refactor
lands and stays a trap thereafter. This is what stops a future component from
quietly growing its own prompt again — the exact drift that produced four
scattered prompts in the first place.

**Behaviour** — the existing component tests must keep passing.
`VocabTab.test.jsx` and `TypingExercise.test.jsx` both mock `src/lib/claude`,
so they assert on parsed replies rather than prompt text; a correct refactor
leaves them untouched.

**`ChatTab` has no test file at all.** Its prompt is the largest and most
structured of the four, and nothing covers it. This phase does not add
component tests for it — that is a separate gap — but it does mean
`chatSystemPrompt`'s unit tests in `prompts.test.js` are the *only* safety net
for the chat prompt. Weight them accordingly: they should assert every part of
the composed string, not a sample.

---

## 8 · Risks

| Risk | Mitigation |
|---|---|
| Level-key casing regression | Lowercase is a decision row (§3), validated in `validate.js`, and pinned by the "never emits `undefined`" test |
| A component regrows a local prompt | Source guard (§7) |
| Persona disagrees with the greeting and chat tasks | Documented in §4 as a Phase 1.5 gap, not a bug |
| Prompt wording changes alter model behaviour | Composition must reproduce today's strings verbatim where the text is unchanged; the refactor moves text, it does not rewrite it |
| `ChatTab` has no component test | `prompts.test.js` is the only net for the largest prompt — assert its composed string exhaustively (§7) |

---

## 9 · Success criteria

1. No prompt text exists outside `src/lib/prompts.js`, enforced by a test.
2. Every JSON output contract is engine-owned; no pack can alter one.
3. The German pack declares persona, target language, per-level pedagogy,
   per-level exercise focus and deck samples — and `validate.js` enforces all
   of it.
4. Existing component tests pass unmodified.
5. A second pack can supply its own prompts without touching engine code —
   the Phase 3 unblock.
