---

## Scope

German grammar is hardcoded in the **engine's data contract**, not merely in
display. Phase 1.4 moves the German-specific *values* behind `pack.grammar`
while leaving the lexicon's field names and its 2.3 MB of shipped data
untouched.

Out of scope: renaming schema fields, the `POS` list, article position, and
`src/data/content.js` (Phase 1.5). See §6 for the three limits this leaves in
place deliberately.

---

## Why

### The German is in the contract, not the components

Every prior phase moved language out of a *presentation* path. This one is
different: the assumptions live in `validateLexiconEntry`, which decides
whether a pack's lexicon is loadable at all.

As of `main` @ `a06c743`:

| Location | German assumption |
|---|---|
| `validate.js:118` | `ARTICLES = ['der', 'die', 'das']` |
| `validate.js:146` | a noun without an article is rejected |
| `validate.js:181` | `verb.aux` must be `haben` or `sein` |
| `validate.js:188` | `verb.present` keyed `ich/du/er/wir/ihr/sie` |
| `verbDisplay.js:8` | shows `present.er` specifically |
| `verbDisplay.js:13` | `aux === 'sein' ? 'ist' : 'hat'` |
| `verbDisplay.js:14,16` | labels `Perfekt`, `Part. II` |

A Spanish pack fails at the **first** of these: `el` is not in `ARTICLES`, so
not one entry validates.

### An existing duplication

`validate.js:119` hardcodes `CEFR = ['A1','A2','B1']` for `entry.cefr` while
`meta.cefrLevels` is already pack-declared. Two sources of truth for one list,
and only one of them is a pack's to change.

### Why the data shape is not touched

The lexicon is ~2.3 MB across nine `public/lexicon/chunk-*.json` files, and
`scripts/import-lexicon/` (`parseWiktextract.js`, `mapEntry.js`, `filter.js`)
encodes German grammar throughout. Renaming `partizip2` would mean
regenerating every chunk and reworking the importer — a much larger phase with
real risk to shipped content, for a naming improvement.

Field names become **slots a pack fills** rather than German-only fields. Each
pack brings its own importer anyway, so a German-flavoured slot name costs a
future pack author a line of documentation, not a migration.

## Decisions

| # | Decision | Choice |
|---|---|---|
| 1 | Scope | **Abstract the values; keep the field names.** No data migration, importer untouched |
| 2 | Verb display | **Structured fields, engine keeps the algorithm.** Not line specs, not a pack-supplied function |
| 3 | `articleRequiredForNouns` | **In.** It is a hard gate — a pack whose language works differently cannot load a lexicon at all |
| 4 | `POS` list | **Stays engine-owned.** Same failure mode, far less likely to bite a European pack 2 |
| 5 | Article position | **Stays hardcoded.** Every likely pack 2 puts the article first |
| 6 | New parameters | **No defaults.** Explicit `grammar` argument at both call sites |

Decision 2 follows the precedent Phases 1.2 and 1.3 both set, for the same
reasons: validatable, testable without a consumer, serializable for Phase 4.
A language with no auxiliary-perfect construction declares no auxiliaries and
that display line simply never renders.

Decision 6 costs test churn — see §5. The alternative, defaulting `grammar` to
`activePack.grammar`, would spare it by dragging the pack registry into a pure
module. That is the implicit coupling the last two phases removed.

## 1 · The contract

```js
// src/packs/de/index.js
grammar: {
  // Nouns
  articles: ['der', 'die', 'das'],
  articleRequiredForNouns: true,

  // Verbs
  auxiliaries: { haben: 'hat', sein: 'ist' },   // aux key → 3sg form for the perfect
  personKeys: ['ich', 'du', 'er', 'wir', 'ihr', 'sie'],
  displayPerson: 'er',                           // the person the vocab card shows

  labels: { perfect: 'Perfekt', participle: 'Part. II' },
}
```

`displayPerson` doubles as that line's label, which is exactly what
`formatVerb` does today — `{ label: 'er', value: present.er }`. A separate
`labels.person` would be a second source of truth free to drift from the key
it describes.

`auxiliaries` is a **map, not a list**, because the engine needs both the set
of legal `aux` values (for validation) and each one's third-person-singular
form (for display). A list would need a second parallel structure.

Every field is required. No defaulting to German.

---

## 2 · Signature changes

```js
formatVerb(verb, grammar) → { label, value }[]
validateLexiconEntry(entry, { grammar, cefrLevels }) → true
```

`validateLexiconEntry` takes an options object rather than the whole pack: the
import pipeline builds entries *before* a pack exists, and should not have to
construct one to validate its own output.

`validateLanguagePack` gains a `grammar` shape check (§4) and passes nothing
new — it already holds the whole pack.

---

## 3 · The engine algorithm stays put

`formatVerb` keeps its order and composition; only the values it reads become
pack-supplied:

```js
export function formatVerb(verb, grammar) {
  if (!verb || typeof verb !== 'object') return [];
  const lines = [];
  const person = grammar.displayPerson;
  if (verb.present?.[person]) {
    lines.push({ label: person, value: verb.present[person] });
  }
  if (verb.partizip2) {
    const aux3sg = grammar.auxiliaries[verb.aux];
    if (aux3sg) {
      lines.push({ label: grammar.labels.perfect, value: `${aux3sg} ${verb.partizip2}` });
    } else {
      lines.push({ label: grammar.labels.participle, value: verb.partizip2 });
    }
  }
  return lines;
}
```

### One behaviour change, and it is an improvement

Today an **unrecognised** auxiliary formats as `hat`, because the rule is
`aux === 'sein' ? 'ist' : 'hat'` — anything that is not `sein` gets the
`haben` form. Under `grammar.auxiliaries[verb.aux]` an unknown value yields
`undefined` and falls through to the participle-only line.

`validateLexiconEntry` gates `aux` to the declared auxiliaries, so a valid
pack cannot reach this path. The change matters only for malformed data, where
falling back is more honest than guessing. Worth a test either way.

## 4 · Validation

`validateLanguagePack` gains a `grammar` check:

- `grammar` is an object
- `articles` is an array of non-empty strings. **The array itself may be
  empty** — a language with no articles states that explicitly rather than
  omitting the field
- `articleRequiredForNouns` is a boolean
- `auxiliaries` is an object whose every value is a non-empty string
- `personKeys` is a non-empty array of non-empty strings
- `displayPerson` is a non-empty string **and a member of `personKeys`**
- `labels.perfect` and `labels.participle` are non-empty strings
- `articles: []` together with `articleRequiredForNouns: true` is **rejected**
  — no article could ever satisfy it, so every noun in that pack's lexicon
  would fail. Better to name the contradiction at startup than to let a pack
  author debug it one entry at a time

The `displayPerson ∈ personKeys` rule is the one worth having. Violating it
does not throw at render time — `verb.present[person]` is `undefined`, the
line silently never renders, and the vocab card just quietly loses its
conjugation row. Exactly the class of failure Phase 1.3's level-key trap had.

`validateLexiconEntry` changes:

- `entry.article` must be `null` or a member of `grammar.articles`
- a noun with `article: null` fails **only when** `articleRequiredForNouns`
- `entry.verb.aux` must be `null` or a key of `grammar.auxiliaries`
- `entry.verb.present` is checked over `grammar.personKeys`
- `entry.cefr` must be `null` or a member of `cefrLevels`

The `ARTICLES` and `CEFR` exports are **removed**. `POS` stays (Decision 4).

Failures throw at startup naming the field, as every other contract violation
does. No runtime fallback: a pack whose grammar is malformed should not boot.

## 5 · Testing

**This phase changes test files, and that is expected.** Phases 1.2 and 1.3
each held a "no test file changes" gate because both were pure refactors
behind unchanged signatures. Here the signatures change, so the churn is
inherent rather than a signal that behaviour moved. Do not apply the earlier
phases' rule to this one.

The churn, measured:

| File | `validateLexiconEntry` calls |
|---|---|
| `src/packs/validate.test.js` | 17 |
| `scripts/import-lexicon/mapEntry.test.js` | 2 |
| `src/packs/de/lexicon.test.js` | 1 |
| `src/packs/lexiconSample.test.js` | 1 |

plus **9** `formatVerb` calls in `src/lib/verbDisplay.test.js` and one in
`VocabTab.jsx`.

`validate.test.js:251-254` asserts the `POS` / `ARTICLES` / `CEFR` exports
exist with German values. It must lose its `ARTICLES` and `CEFR` assertions;
the `POS` one stays.

**What still must not change:** `VocabTab.test.jsx` and every other component
test. The rendered output of the vocab card is identical — only where
`formatVerb` gets its values changed. A component test needing an edit means
real behaviour moved.

**New coverage:**

- `formatVerb` under a non-German grammar — a fixture with
  `displayPerson: 'il'`, `auxiliaries: { avoir: 'a', être: 'est' }`, French
  labels — producing correctly-shaped lines. This is the assertion that proves
  the abstraction actually abstracts, rather than merely relocating German.
- `formatVerb` with an auxiliary absent from `auxiliaries` falls to the
  participle line (§3).
- `validateLanguagePack` rejects: missing `grammar`; non-boolean
  `articleRequiredForNouns`; an `auxiliaries` value that is not a string; an
  empty `personKeys`; **`displayPerson` not in `personKeys`**.
- `validateLexiconEntry` accepts a Spanish-shaped noun (`article: 'el'`) under
  a Spanish grammar, and rejects it under the German one. The pair is the
  point: same entry, different verdict, decided entirely by the pack.
- `validateLexiconEntry` accepts an article-less noun when
  `articleRequiredForNouns` is `false`.

**Unchanged and load-bearing:** `de/lexicon.test.js` validates every real
lexicon entry. It must still pass against the German grammar — that is the
proof no shipped data was invalidated.

## 6 · Three limits, deliberately left

**Article position.** `resolve.js:8` composes `${article} ${de}` — `der Hund`.
Wrong for Romanian or Scandinavian, which suffix the article. Every likely
pack 2 (Spanish, French, Italian) puts it first, so this is speculative
generality; a pack that needs it will know, and adding the field then is
cheap.

**The `POS` list.** Still engine-owned:
`['noun','verb','adj','adv','prep','num','phrase','pron','conj']`. A Japanese
pack needing `particle`, or Chinese needing `classifier`, would have its
entries rejected outright. Same failure mode as `articles`, but a European
pack 2 is unaffected.

**A third level list.** Self-review turned up `src/lib/stats.js:23` —
`LEVELS = ['a1','a2','b1']`, lowercase, driving the `byLevel` stats buckets
and throwing on an unrecognised level (`stats.js:82`). That makes three lists
of the same thing: `meta.cefrLevels`, the `CEFR` constant this phase removes,
and this one. It is **not grammar**, so it stays out of 1.4 — and a European
pack 2 uses CEFR anyway, so it does not block Phase 3. Recorded because it is
the last hardcoded level list standing, and whoever picks up Phase 4 should
know it exists.

All three are recorded here so that a future pack author hits a documented
limit rather than an unexplained rejection.

## 8 · Risks

| Risk | Mitigation |
|---|---|
| A shipped lexicon entry stops validating | `de/lexicon.test.js` validates every real entry and must stay green (§5) |
| `displayPerson` drifts from `personKeys` | Validated explicitly; the failure is silent at render time (§4) |
| Test churn hides a real behaviour change | Component tests must stay untouched; only signature-bearing tests change (§5) |
| The abstraction merely relocates German | The non-German `formatVerb` fixture is the check (§5) |

---

## 9 · Success criteria

1. No German grammar value is hardcoded in `src/lib/` or `src/packs/*.js` —
   only in `src/packs/de/`.
2. `entry.cefr` validates against `meta.cefrLevels`; the `CEFR` constant is
   gone.
3. `formatVerb` produces correct lines for a non-German grammar fixture.
4. Every real lexicon entry still validates, and every component test passes
   unmodified.
5. A second pack can declare its own articles, auxiliaries and persons without
   touching engine code — the Phase 3 unblock.
