# Dev toolkit — safe navigation & anti-cruft

Lightweight shortcuts to **pull up any element** of the project and keep stale
**cache/cruft** from piling up — so development and maintenance stay fast and
safe. No new runtime dependencies; pure-Node scripts + one Claude skill.

## Call up an element

See a component/module and its **dependency blast radius** before editing it.

| Action | Command |
| --- | --- |
| Locate an element + who depends on it | `npm run where -- <name>` |
| Same, from Claude | `/component <name>` |

```
$ npm run where -- GoalRing

▶ src/components/gamification/GoalRing.jsx
    exports: default
    imports (1): src/lib/theme.js
    depended on by (2):
        - src/App.jsx
        - src/components/gamification/GoalRing.test.jsx
```

The **depended on by** list is the safety net: change `X`, then re-check and
re-test everything that depends on `X`.

## Avoid collecting unnecessary cache / cruft

Covers the four staleness sources, lightest-touch first:

| Concern | Tool / status |
| --- | --- |
| **Dead / duplicate code** | `npm run audit:dead` — modules under `src/` that no non-test module imports. Heuristic — review before deleting. |
| **Build / dev cache** | `npm run clean` — removes `node_modules/.vite`, `.vite`, `dist`, `dev-dist`, `coverage`. All regenerated by the next dev/build. |
| **Stale PWA / service-worker** | Already handled — `vite.config.js` uses `registerType: 'autoUpdate'`, so vite-plugin-pwa installs new versions and cleans outdated caches automatically. Nothing to run. |
| **Stale app state / storage** | See the storage-key reference + reset below. |

### Stale app state / localStorage

The app owns exactly these keys (keep this list current if you add one):

| Key | Owner | Purpose |
| --- | --- | --- |
| `deutsch-app-state-v1` | `src/lib/storage.js` | Main state blob (srs, daily, stats, gamification, learnedWords). |
| `deutsch-app-sync-meta-v1` | `src/lib/sync/syncMeta.js` | Sync baseline/cursor metadata. |
| `deutsch-level` | `src/App.jsx` | Selected CEFR level (a1/a2/b1). |
| `deutsch-onboarded` | `src/App.jsx` | Onboarding/splash completed flag. |
| `deutsch-welcome-dismissed` | chat welcome banner | Welcome banner dismissed flag. |

To blow away local state safely during development (browser console on the app
origin):

```js
Object.keys(localStorage).filter((k) => k.startsWith('deutsch')).forEach((k) => localStorage.removeItem(k));
location.reload();
```

## How it works

- `scripts/lib/moduleGraph.js` — **pure**, I/O-free parsing + graph logic
  (imports, dependents, purpose, exports, orphans). Unit-tested in
  `scripts/lib/moduleGraph.test.js` and run as part of `npm test`.
- `scripts/lib/collect.js` — the only fs-touching piece (walks `src/`/`api/`).
- `scripts/where.js`, `scripts/audit-dead.js`, `scripts/clean.js` — thin CLIs.
- `.claude/skills/component/SKILL.md` — the `/component` shortcut.

Heuristics are regex-based and tuned to this repo's tidy top-of-file imports;
they don't follow dynamic `import()` or runtime indirection. Treat output as a
strong hint, not proof.

## Agent & tooling config

`.claude/skills/component/SKILL.md` above is one of several agent files this
repo tracks on purpose. The full table, and the rules that go with them, live
in **`AGENTS.md` → "Agent & tooling config"**. The short version:

| Path | What it is |
| --- | --- |
| `.mcp.json`, `.cursor/mcp.json`, `.codex/config.toml` | The Supabase MCP server, once per agent format. |
| `.cursor/rules/deutsch-app.mdc` | Cursor's always-apply rule; points at `AGENTS.md`. |
| `.claude/launch.json` | Named dev servers for the preview tool — use these, not `npm run dev` through a shell. |
| `.claude/skills/component/SKILL.md` | First-party; backs `/component` and `npm run where`. |
| `.agents/skills/**`, `.claude/skills/supabase*` | Vendored third-party skills, hash-pinned by `skills-lock.json`. Deliberate duplicates — `.agents/` is tool-neutral, `.claude/skills/` is what Claude Code reads. |

Per-machine files — `.claude/settings.local.json`, `.claude/worktrees/`,
`.cursor/settings.json`, `.superpowers/` — are ignored in `.gitignore` and must
never be tracked.

> [!WARNING]
> **The MCP config points at the production Supabase project**
> (`project_ref=xcnnlczvxmuwcqwychox`). There is no staging project. Opening
> this repo in any agent connects it to the live database with write-capable
> tools. Never run `supabase migration repair`, `db push`, `db pull`, or
> `db reset` against it, and never apply a migration or mutate production data
> through the MCP without the owner's explicit approval. Reads are fine.

On the two migration checks: **`Migration Drift` is the source of truth** — it
asks whether production has every migration the repo committed, and it is
deliberately not a required check. **`Supabase Preview` is not required and is
currently red**; it asks the inverse question and disagrees by design, because
7 migrations applied through the MCP carry application-time version stamps
rather than the filename's authoring time. Ignore it — don't "fix" it by
applying or repairing migrations.

See also `docs/MAINTENANCE_CHECKLIST.md` for how this fits the release flow.
